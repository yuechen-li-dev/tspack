# TSPack v0.1.5

Planned release notes for the next public patch release.

## Theme

Incremental adoption for existing npm projects.

## Highlights

- Add TSPack beside an existing `package.json` project with `tspack init --alongside`.
- Observe npm-native project state without writing files with `tspack adopt --report`.
- Delegate package-manager operations explicitly with `tspack npm <args...>`.
- Explain observed npm dependency reachability with `tspack why <package>`.
- Surface observed lifecycle/security capability warnings with `tspack adopt --security`.
- Add package annotation mode with `annotatePackage(<PackageAnnotations />)`.
- Suggest annotation scaffolds with `tspack adopt --suggest-package <package-root>`.
- Validate annotation consistency with `tspack adopt --check-annotations`.
- Manage manifest-declared JSON/editor compatibility files with `tspack compat list`, `tspack compat diff`, and `tspack compat write`.
- Improve manifest editor support, local manifest types materialization, cold-store progress output, and missing-Node diagnostics.

## Incremental adoption

`tspack init --alongside` adds a root `manifest.tsx` beside an existing npm project without taking over `package.json`, `package-lock.json`, or npm execution. From there, `tspack adopt --report` gives a read-only view of project metadata and `tspack why <package>` explains direct or observed dependency presence before a full TSPack migration.

`tspack npm <args...>` makes the compatibility boundary explicit: TSPack can describe and audit the project while npm remains the package materialization engine. This keeps adoption incremental instead of forcing an all-at-once migration.

## Compatibility and meta management

This release expands manifest-declared compatibility file support with `<CompatFiles>`, `<JsonFile>`, `TsConfig.manifestEditor()`, `VSCode.settings()`, and `VSCode.extensions()`. Existing projects can inspect and materialize these files explicitly with `tspack compat list`, `tspack compat diff`, and `tspack compat write`.

The manifest editor path is also more reliable for alongside projects: compat writes materialize `.tspack/types/tspack-manifest.d.ts`, reducing red-squiggle friction in editors and making the intended TSX authoring path more consistent.

## Package annotations

`package.manifest.tsx` annotation mode lets an existing npm package describe dependency intent with `annotatePackage(<PackageAnnotations />)` without claiming full package ownership. `tspack adopt --suggest-package` provides a reviewable annotation draft, and `tspack adopt --check-annotations` validates annotation/package.json consistency.

## Security and lifecycle visibility

`tspack adopt --security` adds a read-only audit surface for observed npm lifecycle capabilities. It reports what was found, where the evidence came from, and the dependency chains involved without executing scripts, fetching registry data, or rewriting project files.

## Template and concept system

The template/concept MVP continues to advance with concept fragment composition, explicit concept stack semantics, local concept fragments, local Tailwind and MachinaLayout fixtures, and a built-in concept promotion policy. These changes broaden the template foundation, but incremental adoption remains the primary release headline.

## UX and editor polish

- Fix manifest TSX editor support and local declaration materialization for alongside projects.
- Print plain progress during cold store fetch/materialize work.
- Improve missing Node diagnostics with direct `mise` guidance.
- Keep CLI/help text aligned with the new adoption and compat commands.

## Breaking changes

None verified at audit time.

## Upgrade notes

- Existing npm projects can start with `tspack adopt --report` and `tspack init --alongside` before attempting full migration.
- After `init --alongside`, run `tspack compat diff` and `tspack compat write` explicitly to materialize editor support files.
- `tspack npm run ...` delegates to npm scripts; `tspack run ...` remains for manifest-declared RunTargets only.
- Annotation mode is advisory metadata for existing npm packages, not full package ownership.
