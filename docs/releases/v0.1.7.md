# TSPack v0.1.7

TSPack v0.1.7 is the stabilization and performance patch that tightens generated-project editor support, makes VS Code and TypeScript SDK selection more predictable, and materially improves cold update and repeated sync behavior on the current TypeScript/npm path.

## Highlights

- Clean manifest and xTest editor support for generated and compat-managed projects.
- Managed workspace TypeScript SDK guidance for VS Code consistency.
- Deterministic parallel resolver preparation for faster cold updates.
- Artifact capture during resolve so post-resolve store population usually has little or no remaining work.
- Hardlink-first `node_modules` materialization with copy fallback only when hardlinks are unavailable.
- Materialization marker fast path plus `tspack sync --force` for intentional rematerialization.
- Performance harness and pprof capture for repeatable update and sync benchmarking.
- Experimental feedforward resolver occupancy controller behind configuration; default remains `fixed`.

## Editor and manifest support

This release continues the M64 editor and manifest cleanup:

- generated `.tspack/types/tspack-manifest.d.ts`
- generated `.tspack/types/tspack-xtest.d.ts`
- `tsconfig.tspack.json` isolation with `"types": []`
- `src/*.xtest.tsx` inclusion where expected
- configurable `TsConfig.manifestEditor({ include, exclude })`
- solution-style TypeScript discovery configs where needed
- cleaner VS Code project routing with fewer red-squiggle and wrong-project cases

For day-to-day use, that means a fresh or compat-managed project is much closer to "install Node, install TSPack, start writing TypeScript" without hand-fixing editor routing.

## Managed TypeScript and VS Code consistency

M65 adds a more intentional editor/tooling path:

- generated `.vscode/settings.json` points VS Code at the workspace TypeScript SDK
- the TSPack repository itself uses the nested workspace SDK path consistently
- hardlink-first materialization reduces duplicate copy work during `sync`

This does not make TSPack a Node runtime manager. You still need a working Node on `PATH`, and `mise` remains the recommended runtime manager.

## Performance

M66 and M67 focus on cold-update throughput and diagnosability without changing resolver semantics:

- tuned HTTP transport
- metadata memoization
- artifact capture during resolution
- store population skip when artifacts were already captured
- deterministic parallel resolver preparation with serial deterministic commit
- no-op warm sync marker fast path
- benchmark and pprof harness for update and sync profiling

On one Windows 11 benchmark pass using the React template, fixed parallel cold update with `TSPACK_RESOLVE_JOBS=24` averaged `7.80s` versus a `24.70s` forced-serial baseline, and repeated warm sync averaged `0.23s` after the materialization marker fast path. The same pass captured `121` artifacts during resolve, spent effectively zero time fetching store artifacts afterward, and first sync materialized `10716` files through hardlinks with `0` copy fallbacks on that machine.

Those numbers are local benchmark evidence, not universal promises.

## Sync and materialization

`tspack sync` is more predictable and cheaper to repeat in v0.1.7:

- hardlink-first package file materialization reduces duplicate disk copy work
- warm sync becomes near no-op when the materialization plan is unchanged
- `tspack sync --force` intentionally ignores the current marker and rematerializes
- fresh-machine sync can hydrate missing local store artifacts from locked sources without changing selected versions

In the current-main benchmark closeout, warm sync skipped `329` packages and `10716` files once the marker was current.

## Incremental adoption and compatibility

The v0.1.5 incremental-adoption work remains part of the current release story:

- compat-managed files still provide the explicit bridge between TSPack manifests and existing editor/project surfaces
- `tspack compat diff` and `tspack compat write` remain the supported way to materialize generated TS and VS Code files
- TSPack still delegates npm operations explicitly through `tspack npm ...` rather than pretending to emulate npm

v0.1.7 does not replace that compatibility boundary; it makes the editor and generated-file path cleaner and more reliable.

## Experimental controller notes

TSPack now has two resolver occupancy controller modes:

- `TSPACK_RESOLVE_CONTROLLER=fixed`
- `TSPACK_RESOLVE_CONTROLLER=feedforward`

Related controls:

- `TSPACK_RESOLVE_JOBS` sets the resolver cap
- `TSPACK_STORE_JOBS` controls bounded store work

The experimental `feedforward` mode is available for benchmarking and validation, but the v0.1.7 default remains `fixed`. In the current local benchmark pass, feedforward did not clearly beat the stabilized fixed default.

## Validation and compatibility

Release-prep validation for v0.1.7 includes:

- full `go test ./... -timeout 300s`
- manifest frontend build, manifest API typecheck, and frontend tests
- VS Code extension compile and tests
- root compat diff and manifest editor TypeScript file-list validation
- local release artifact build, checksum generation, extraction, and CLI smoke
- fresh project dogfood for `init`, `update`, `sync`, repeated `sync`, and manifest-editor type surfaces

The release workflow, installer, and setup action all continue to use GitHub Releases plus `checksums.txt` rather than introducing a new distribution channel in this patch.

## Known limitations

- TSPack remains early and not production-stable.
- `feedforward` occupancy control is still experimental and not the default.
- Benchmark numbers in the docs are from local controlled runs, not cross-machine guarantees.
- TSPack does not manage Node.js runtime versions.
- `get.tspack.dev`, Homebrew, mise plugin distribution, and a separate `setup-tspack` repository remain future work.
