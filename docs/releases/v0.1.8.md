# TSPack v0.1.8

TSPack v0.1.8 makes CI and dependency operations easier to trust and diagnose. It adds a native OSV-backed audit command, an explicit project minimum-version contract, better dependency-change attribution, structured manifest errors, and Windows lock-owner diagnostics.

## Highlights

- `tspack audit` checks exact npm versions from `ts-lock.toml` against OSV.dev without invoking npm or mutating project state.
- `.tspack-version` declares the minimum compatible TSPack release for local commands and CI.
- The first-party setup action enforces `.tspack-version` after resolving the requested release.
- Manifest frontend JSON diagnostics survive nonzero frontend exits instead of collapsing into a generic bridge failure.
- Update output distinguishes direct and transitive package changes and calls out unusually broad updates.
- Windows materialization failures identify the process and PID holding a destination file when Restart Manager can resolve it.

## Native vulnerability audit

Run `tspack audit` after resolving a lockfile. TSPack batches exact npm package coordinates through OSV.dev and reports the advisory, severity, fixed versions when known, and dependency paths.

Any known vulnerability fails by default. `--audit-level moderate`, `high`, or `critical` can raise the CI failure threshold, while `--json` provides stable machine-readable output. Network failures, malformed responses, and incomplete advisory detail fail closed rather than producing a false clean result.

The audit is intentionally read-only. It does not execute lifecycle scripts, inspect mutable `node_modules`, rewrite the manifest or lockfile, or automatically select upgrades.

## Minimum-version contract

A project may place one semantic version in `.tspack-version`. Commands that evaluate the project contract reject an older CLI with `TSPACK_VERSION_TOO_OLD` before invoking the manifest frontend. Generated templates now include this file.

The setup action reads `.tspack-version` by default through its `version-file` input and verifies that the installed release meets the declared minimum. This keeps local and CI compatibility failures early and explicit.

## Diagnostics and update clarity

Structured diagnostics emitted by the manifest frontend are now preserved even when the frontend exits nonzero. Generic stdout/stderr fallback remains available for unstructured failures.

Update summaries label dependency mutations as direct or transitive. Large mutation sets also include a hint to review the broad change, making targeted upgrades and unexpected graph churn easier to distinguish.

On Windows, locked-file replacement errors now consult Restart Manager and include the owning process name and PID when available.

## Validation

Release validation includes the full Go test suite, manifest frontend tests, setup-action tests, release packaging, and a real website dogfood pass covering check, formatting, typecheck, build, documentation validation, and native audit.

## Compatibility and limitations

- TSPack remains early and not production-stable.
- Vulnerability data depends on OSV.dev availability and advisory completeness.
- TSPack reports fixed versions from advisory data but does not automatically remediate findings.
- Lock-owner details are best-effort and currently use the Windows Restart Manager API.
- TSPack still requires a working Node.js runtime for manifest evaluation and does not manage Node versions.
